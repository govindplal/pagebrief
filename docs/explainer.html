Everything you need to explain this project: what it does, the order things were built in and what each step taught, the honest conclusion from 840 benchmark runs, every concept and architecture used (with the reason it was chosen over the alternative), likely interview questions, a self-quiz, and a reading list.

TL;DR

AI agents read web pages through "browser tools" that are expensive: most of the cost is not the page, it is the tool definitions sent on every turn. pagebrief is an MCP server that drives Chrome directly over the DevTools Protocol and gives the agent a short, typed view of a page in one call. For page types it has seen before, it answers from page maps: field locations a large model wrote once, checked by plain code on every load.

Result: 4.8x fewer tokens than Playwright MCP at 100% success, but only 1.1x cheaper per task (cached tokens are cheap) and about 2 seconds slower. On repeat visits with a map: 3.5x cheaper at the same speed.

01

The pitch

Three lengths. Learn the short one by heart and expand only when asked.

10 seconds

I built an MCP server that lets AI agents read web pages for a fraction of the tokens, and benchmarked it against Playwright MCP on 840 agent runs.

30 seconds

Agents browse the web through tools like Playwright MCP, but I measured that most of their tokens go to tool definitions re-sent every turn, not to page content. So I built pagebrief: a few small tools, Chrome driven over raw CDP, and a typed page view in one call. For repeat page types, a large model writes a "map" of where fields live once, and plain code validates it on every load, failing closed to text. It uses 4.8x fewer tokens than Playwright MCP at the same accuracy, and repeat visits are 3.5x cheaper.

2 minutes, the honest version

Add: I wrote the benchmark before the engine, which changed the design. The token win did not become an equal cost win because re-sent definitions are prompt-cache reads, billed at about a tenth of the input price, so the per-task saving on first visits is small. I'm also slower than Playwright MCP on seconds, which I report openly. The real lever turned out to be repeat visits: a validated map removes most of the model's reading work. Safety-wise it refuses private-network URLs (SSRF), labels every action by risk, and treats page text as untrusted.

02

What the project does

pagebrief sits between an AI agent and a real browser. The agent never drives the browser itself; it asks for a page and gets an answer-ready view.

open(url)

Loads the page in headless Chrome, captures the JSON the page fetched, and returns title, structured data, forms, and the start of the visible text. If a map exists, checked typed fields come first.

find(pattern) · read(from)

Search everything on the page (text, links, JSON values) with a regex, or read the next slice, without re-sending the page.

do(...)

Off by default. Clicks, fills, submits, each labelled read / write / dangerous, capped by a policy. Returns a diff of what changed.

03

Architecture

Layered, with one stable surface at the top. Each band can be replaced without touching the one above it. This is the ports-and-adapters idea: the agent-facing port stays fixed, the browser and model are adapters.

The Llm interface has two adapters: Claude through claude -p on a subscription, and any Ollama model. The browser adapter can be Chrome launched locally or any CDP endpoint.

04

How we got here

The order matters for an interview story: each step was a response to something measured, not a feature list written in advance.

step 1 · benchmark first

Measure before building

60 reading tasks on 20 stable public sites, each answer verified against page HTML or the site's API. Headless Claude Code drives each tool. First finding: on Playwright MCP a median task took about 26k tokens but only about 2k characters of that was page content; most was tool definitions (~8k tokens) re-sent every turn. agent-browser sent ~22k tokens of definitions per turn.

Lesson: the expensive part is the tool surface and the number of turns, not the page.
step 2 · engine v0.1

Three small tools over raw CDP

open, find, read, about 1,300 characters of definitions in total. One Runtime.evaluate to extract the page, and the page's own JSON captured from the Network domain. Measured 2026-11-09: 95% success, 5,346 median tokens (4.9x fewer than Playwright MCP), 12.7 s.

Lesson: an answer-ready view means most lookups take one call.
step 3 · v0.1b

Interaction-heavy pages

Better search over JSON documents and pages that need interaction. These still cost about 20k tokens at the median, which pointed at actions as future work.

step 4 · v0.2 hardening

A review found what the benchmark could not see

open accepted any URL, so a page could steer an agent to localhost or a cloud metadata address (SSRF). Parallel opens raced on one tab. Analytics JSON crowded out real data. Fixes: a private-network guard with DNS and redirect checks, a queue so opens run one at a time, JSON ranking (own site first, trackers last), main-content start.

Lesson: friendly benchmark sites hide security and concurrency bugs. Review the code separately from the numbers.
step 5 · rename + CI

agentic-browser → pagebrief

The npm name belonged to another package. Added GitHub Actions on Ubuntu and Windows, including a clean install from the packed tarball, so packaging bugs show up before users do.

step 6 · v0.3 page maps

Make repeat visits nearly free

Teacher writes a map once per page type; checker validates every field on every load; student repairs; grader labels failures. Also: bot-check and login-wall reports, invisible-text drop, several open pages, a repeat-visit benchmark track, tool-search mode, hex.pm replacing openlibrary.org (which began serving bot checks).

step 7 · actions + more

Actions, external browsers, sharing, baselines

The do tool with risk labels and diffs; --cdp-url for any CDP browser; map export and import with screening; a screenshot baseline; a campaign driver that waits across 5-hour usage windows.

step 8 · the number bug

A wrong value passed every check

hex.pm prints downloads as "168 360" with a space between thousands. The parser read 168. Type and shape checks passed, so the agent would have got a confidently wrong number. Fixed the parser with tests, re-taught the maps with claude-opus-5-5, reran the map evaluation.

Lesson: validation that only checks types can still pass wrong values. Test the parser on real-world formats.
step 9 · campaign

840 runs across three tracks

Main track (5 tools), tool-search track (4 tools), repeat-visit track (5 tools including mapped pagebrief). Stopped automatically at 85% of each 5-hour quota window and resumed after the reset.

06

Conclusion

What held up
A small tool surface plus an answer-ready view cuts tokens about 5x at equal accuracy.
Validated page maps make repeat visits about 3.5x cheaper, with a model call only once per page type.
Fail-closed checks: on a failed check the agent sees text, never a wrong value.
What did not
Tokens are not cost. Re-sent definitions are cache reads, so a 4.8x token cut gave a 1.1x cost cut on first visits.
Seconds: about 2 s slower than Playwright MCP on the main track. The project's own target is not met.
With tool search on, rivals stop paying for definitions, and the gap narrows (still 1.6x cheaper).
The one-sentence conclusion. For one-off reads, a lean tool surface is a modest win once caching is priced in. The durable advantage is repeat visits to the same page types, where a validated map replaces most of the model's reading.

What I would do next, or differently

  • Profile latency (settle wait, extraction) before adding features; seconds is the open target.
  • Run three repeats from the start so differences come with error bars.
  • Measure maps on sites they were not taught on; that is the real generalisation test.
  • Test number and date parsing against a corpus of real formats earlier; the hex.pm bug was avoidable.

Concepts and architectures used

Each card: what it is, where it lives in the code, why it was chosen, what was passed over, and where to learn it.

AI · protocol

Model Context Protocol (MCP)

What
An open protocol for giving models tools. A client (Claude Code) talks to a server (pagebrief) over JSON-RPC 2.0, here on stdio. The server lists tools with JSON-schema inputs; the model calls them.
Where
src/mcp.ts, official TypeScript SDK
Why
Any MCP client can use it unchanged; the SDK handles version negotiation.
Not
A hand-written JSON-RPC server, or a client-specific plugin.
modelcontextprotocol.io · JSON-RPC 2.0 spec
AI · cost

Token economics and prompt caching

What
Every turn re-sends the system prompt and all tool definitions. Prompt caching bills repeated prefixes as cheap cache reads. Tool search loads definitions only when needed.
Where
bench/src/claude-runner.ts (ENABLE_TOOL_SEARCH), report cost columns
Why
Explains the central result: 4.8x fewer tokens but 1.1x lower cost.
Not
Reporting tokens alone, which overstates the win.
Anthropic: prompt caching
AI · agents

Tool design for agents

What
Few tools, short descriptions, results the model can act on immediately, so tasks take fewer turns.
Where
Tool descriptions in src/mcp.ts; the view in src/page/view.ts
Why
Turns multiply cost: each one re-sends the definitions.
Not
A full browser API of 25 to 29 tools.
Anthropic: writing tools for agents · Building effective agents
AI · learning

Teacher and student, knowledge distillation

What
A large model labels examples once; a small model learns or follows them. Here the teacher writes maps; the student only repairs broken ones.
Where
src/maps/teacher.ts, student.ts, bench/src/export-sft.ts
Why
Expensive model once per page type, cheap code every load.
Honesty
The student is prompted, not fine-tuned, so it is not called "distilled". The SFT exporter exists; no training has run.
Hinton et al., Distilling the Knowledge in a Neural Network
AI · fine-tuning

SFT, LoRA, GGUF, Ollama

What
Supervised fine-tuning on chat examples; LoRA trains small adapter matrices instead of all weights; GGUF is a file format for running quantised models locally in Ollama.
Where
docs/finetune.md (plan), src/maps/llm.ts (Ollama client)
Why
A local small student would make repairs free and private.
Status
Not run: needs a GPU and a few hundred pages.
LoRA paper · TRL SFTTrainer · Ollama
Browser · protocol

Chrome DevTools Protocol (CDP)

What
The JSON-over-WebSocket protocol that DevTools, Puppeteer and Playwright use underneath. Organised in domains: Page, Network, Runtime, Target.
Where
src/cdp/connection.ts, src/browser.ts
Why
Direct Network-domain access to capture the page's JSON; no Runtime.enable (a known automation fingerprint); any CDP engine can replace Chrome.
Not
Playwright or Puppeteer in the product (kept only as baselines, so the comparison is fair).
CDP reference · Puppeteer docs (to see what it wraps)
Browser · transport

WebSockets in Node

What
A full-duplex connection over one TCP socket. CDP messages carry an id; responses match by id, events have none.
Where
src/cdp/connection.ts, about 80 lines
Why
Node 22+ ships a standard WebSocket client, so no ws dependency.
Concept
Request/response correlation and event dispatch over one channel.
MDN: WebSocket · Node globals
Browser · content

Page representation

What
innerText (rendered text only) versus textContent (all text, hidden too) versus the accessibility tree versus screenshots.
Where
src/page/extract-script.ts
Why
Rendered text with structured data is short and answer-ready; snapshots are verbose, screenshots cost vision tokens.
Trade-off
Text hidden by opacity or off-screen positioning still gets through.
MDN: innerText · MDN: accessibility tree
Web · data

Structured data and captured JSON

What
JSON-LD (schema.org) blocks, meta tags, and the XHR/fetch JSON a single-page app loads before it renders.
Where
src/page/json-rank.ts, map locations json, jsonld, meta
Why
That data is already typed; reading it beats scraping markup.
Detail
Responses ranked own-site first, analytics last; 2 MB cap after decoding.
json-ld.org · schema.org
Web · extraction

Wrapper induction (what a page map is)

What
A classic data-extraction idea: learn a "wrapper" that pulls fields from every page generated by the same template. Page maps are wrappers written by an LLM and checked by code.
Where
src/maps/: types.ts, pattern.ts, apply.ts
Why
Sites render many pages from one template; one map covers them all via a URL pattern.
Risk
Wrappers break on redesigns and A/B tests, hence checks and repair.
Wikipedia: Wrapper (data mining)
Architecture

Ports and adapters

What
Keep the core independent of its edges: define an interface (port), plug implementations (adapters) into it.
Where
The agent-facing MCP surface; the Llm interface (Claude CLI or Ollama); CDP launch or --cdp-url
Why
Swap Chrome for Lightpanda, or Claude for a local model, without touching the agent surface.
Not
Hard-wiring one browser and one model.
Alistair Cockburn: Hexagonal architecture
Architecture

Functional core, imperative shell

What
Put decisions in pure functions (input → output, no I/O); keep side effects in a thin outer layer.
Where
src/page/view.ts and src/maps/apply.ts are pure; browser.ts does the I/O
Why
The rendering and checking logic is unit-tested without a browser.
Gary Bernhardt: Boundaries
Architecture

Fail-closed validation with schemas

What
When unsure, refuse rather than guess. Maps are zod schemas (a discriminated union for locations); every field is read, typed and shape-checked on every load.
Where
src/maps/types.ts, applyMap()
Why
An agent trusts a typed value; a wrong one is worse than a longer text view.
Lesson
Type checks alone passed the hex.pm "168" bug; parsers need real-format tests.
zod.dev
Architecture · concurrency

Serialised work queue

What
Run operations on a shared resource one at a time, in order, like a mutex.
Where
src/engine.ts: opens queued; last 5 pages kept so find/read can name a page
Why
Agents send tool calls in parallel; a shared tab raced and returned the wrong page.
Not
A tab per call (more memory, more state to clean up).
MDN: the event loop
Security

SSRF and the private-network guard

What
Server-side request forgery: tricking a server into fetching internal addresses (localhost, 10.x, 169.254.169.254 cloud metadata).
Where
src/net/guard.ts
How
Refuse private ranges in IPv4, IPv6 and mapped forms, numeric disguises, names that resolve inward; check every redirect hop and the connected address.
Limit
Behind a proxy Chrome reports the proxy's address, so that check is off there.
OWASP: SSRF · RFC 1918
Security

Prompt injection and untrusted content

What
Text on a page that tries to instruct the agent. The model can't reliably tell data from instructions.
Where
Invisible-text drop in extraction; bot-check and login-wall reports in view.ts
Stance
Reduced, not solved: everything returned is untrusted page content, and the README says so.
Simon Willison: prompt injection series
Security

ReDoS (regex denial of service)

What
Nested quantifiers like (a+)+ can take exponential time on certain inputs.
Where
unsafeRegex() in apply.ts; a 2 s search cap and 300-character pattern limit in find
Why
Maps and agents supply regexes; a long page must not stall the server.
OWASP: ReDoS
Security

Least privilege for actions

What
Give an agent the lowest power that does the job. Actions are classified read, write or dangerous, and a policy caps the level.
Where
src/actions/risk.ts
Hard limits
Never types into password fields, never uploads files, whatever the policy.
Caveat
Labels come from words on the element: a guard and advice, not a guarantee.
Principle of least privilege
Evaluation

Benchmark methodology

What
Fixed tasks with a verified answer key; same agent, model and settings per tool; medians (robust to outliers) over means; interleaved tool order so a stopped run stays balanced.
Where
bench/: tasks, runner, scorer, report, campaign driver
Rigor
Engine version and a hash of the maps are recorded; --resume refuses to mix versions. Runs answering without a tool call are scored wrong.
Gaps
One repeat; friendly sites only; some scorer leniency under review.

Rate limits, resumability, idempotence

What
Long jobs must stop safely before a quota and continue later without duplicating work.
Where
Runner reads Claude Code's rate_limit_event; bench/scripts/campaign.ts waits for the window reset
Why

09

Likely interview questions

Open each one, try answering aloud first, then compare.

Why not just use Playwright MCP?

It works, and it scored 100% too. But it exposes a whole browser API, and its definitions and accessibility snapshots make a median task about 26k tokens. For reading tasks, an answer-ready view in one call does the same job with about 5k. Playwright stays in the project as the baseline to beat.

Your tokens dropped 4.8x but cost only 1.1x. Why?

Prompt caching. Tool definitions are the same every turn, so after the first turn they are billed as cache reads at roughly a tenth of the input price. The tokens I removed were mostly cheap tokens. That is why I report cost first and tokens second, and why the real win is repeat visits, where maps remove the expensive reading work.

You are slower than Playwright MCP. Isn't that a failure?

Against my own target, yes, and I say so. The likely causes are the network-quiet wait after load and doing a full extraction on open. The next step is profiling those rather than guessing. On repeat visits with maps, speed is level (8.4 s vs 8.5 s).

What is a page map and how do you trust it?

A JSON document saying, for one page type (host plus URL pattern), where each named field lives: a JSON path, JSON-LD, a meta tag, or a label-anchored regex. A large model writes it once. On every load, plain code reads each field and checks its type and shape. If any check fails, the agent gets the text view instead. An optional field missing 3 loads in a row is treated as a broken location, because a broken location looks the same as a page that lacks the field.

Tell me about a bug you found.

hex.pm prints "168 360" with a space as the thousands separator. The number parser stopped at the space and returned 168, which passed both the integer type check and the shape check. So the checks were technically satisfied by a wrong value. I rewrote the parser to group space, non-breaking and thin-space separators followed by three digits, handled European "1.234,56", made sure "v1.2.3" is not a number, added tests for each, and re-taught the maps. The lesson was that validation needs realistic inputs, not just type checks.

How do you stop the agent from being used to attack internal networks?

An SSRF guard: before navigating, the hostname is resolved and private, loopback, link-local and carrier-NAT ranges are refused in every form, including numeric disguises like http://2130706433. Every redirect hop is checked, and when there's no proxy, the address Chrome actually connected to. It is opt-in to allow private addresses for local development.

How did you make the benchmark fair?

Same tasks, model, effort and harness for every tool; a verified answer key; tool order interleaved per repeat so an early stop is still balanced; a shared working directory so the prompt cache treats tools alike; runs that answer without browsing are scored wrong; versions and map hashes recorded so results are never mixed. Known gaps: one repeat, friendly sites, and a plain-fetch scoring question I'm checking.

Why raw CDP instead of Puppeteer?

Three reasons: I need the Network domain to capture the JSON the page loads, which is central to the typed view; avoiding Runtime.enable removes a common automation fingerprint; and keeping the product on the protocol means any CDP engine (Lightpanda, for example) can replace Chrome via --cdp-url. The CDP client is about 80 lines on Node's built-in WebSocket.

Is the small model "distilled"?

No, and I'm careful about that word. It is a small model prompted to repair maps. The data pipeline for fine-tuning on the teacher's verified labels exists (SFT export, held-out-by-site plan, LoRA), but no model has been trained. Until one is, calling it distilled would be inaccurate.

What would you change if you started again?

Three repeats from day one for error bars, latency profiling alongside token counts, a real-format corpus for number and date parsing, and a held-out set of unseen sites for the maps.

Glossary

Agent
A model that decides which tools to call, in a loop, to finish a task.
MCP server / client
The server offers tools; the client (Claude Code, Cursor) lets a model call them.
Tool definition
The name, description and input schema of a tool, sent to the model so it knows how to call it.
Turn
One model response plus the tool results fed back. Each turn re-sends the context.
Prompt cache
Reuse of an identical prompt prefix across requests, billed at a lower rate.
Tool search
Loading tool definitions only when the model asks for them.
CDP
Chrome DevTools Protocol: JSON messages over WebSocket to control the browser.
Headless
A browser running without a visible window.
Network quiet
Treating a page as loaded when no requests are pending for 500 ms (capped at 5 s).
JSON-LD
Structured data (schema.org vocabulary) embedded in a page for search engines.
Page map
Where each named field lives on one page type, keyed by host and URL pattern.
Teacher / checker / student / grader
Writes maps / validates them every load / repairs them / labels failures offline.
Fail closed
On doubt, refuse or fall back rather than guess.
SSRF
Server-side request forgery: making a server fetch internal addresses.
ReDoS
A regex that takes exponential time on crafted input.
Baseline
The tool every other is compared against (Playwright MCP here).
Median
The middle value; less affected by a few extreme runs than the mean.
SFT / LoRA
Supervised fine-tuning / a cheap fine-tuning method that trains small adapter weights.
