The idea, and what the benchmark taught first

Browser tools for agents expose a whole browser: Playwright MCP has 25 tools, Vercel's agent-browser 29. The project's first step was a benchmark (60 read-only tasks, 20 sites), run before any engine existed. It showed that on a typical task the page is a small part of the cost.

Playwright MCP26.4k
agent-browser77.5k
agentic-browser v0.1b5.3k

Median tokens per task, Sonnet 5.5, one repeat. Playwright's page content is only ~2k characters; most tokens are tool definitions re-sent every turn (~8k tokens for Playwright, ~22k for agent-browser).

So the design follows from that: fewer, shorter tools and fewer turns. open(url) returns an answer-ready view, so most lookups take one call.

What happens when an agent calls open(url)

1
MCP call arrives

The server (src/mcp.ts) exposes three tools with tiny descriptions and passes the call to the engine.

2
Engine checks the URL

src/engine.ts: must be absolute http(s). v0.2: local and private addresses are refused; calls are queued so parallel opens don't race on the single tab.

3
Chrome starts lazily

src/cdp/chrome.ts launches your installed Chrome headless with a throwaway profile and reads its DevTools address. First call only.

4
Navigate and settle

src/browser.ts sends Page.navigate, waits for the load event, then until the network is quiet for 500 ms (capped at 5 s) so data fetched after load is included. It never calls Runtime.enable, a known automation fingerprint.

5
Capture the page's own JSON

From Network.* events, every JSON response is kept (up to 2 MB). Many sites fetch typed data as JSON then render it; reading the JSON skips the scraping.

6
Extract in one evaluate

src/page/extract-script.ts runs inside the page and returns innerText (so CSS-hidden text is dropped), headings, visible links, forms with labels and JSON-LD.

7
Render a compact view

src/page/view.ts: title, URL, description, structured fields, list of captured JSON, forms, then ~3,000 characters of text with a pointer to find / read for the rest. The full page stays in memory.

The interaction fixes on master (v0.1b)

Packagist version data is one big JSON document. Three bugs made it unusable: find searched its text as one giant line; only the first 5,000 values were searched; and the 400k-character text limit made large JSON unparseable. v0.1b searches the captured response by path, searches every value, and shows matches in context.

The benchmark

Design

  • 60 tasks, 20 sites. Sandboxes, versioned or immutable pages and a Wayback snapshot, so answers don't drift. Every answer was checked against page HTML or the site's API, not memory.
  • Agent: headless Claude Code (claude -p) on your subscription, with its own tools, settings, hooks and plugins off. Fixed overhead is 761 tokens, so counts reflect the tool under test.
  • Scoring: the agent ends with ANSWER: …; the scorer accepts number, date (±1 day) and text variants. Runs that never use the browser score wrong.
  • Quota-safe runner: reads Claude Code's rate-limit events, stops at 85% of the 5-hour window, orders jobs repeat-major with tools interleaved so a partial run is still fair, and --resume continues.

Honest gaps

  • Tool search was off in every run, to measure all tools alike. Harnesses that load tools on demand don't pay the 8k–22k per turn that produces most of the 5x. The headline gap is partly an artifact of that setting.
  • No cheaper rival measured: plain-fetch exists but has not run. On friendly read-only sites it may do very well.
  • Tokens are not cost. Re-sent definitions are cache reads at about a tenth of input price; the cost gap is smaller. v0.2's report shows both.
  • One repeat, and concurrency differed (3 vs 2).
  • Friendly sites only; nothing here measures bot blocking, logins or cookie walls.
  • Not built yet: actions, diffs, the per-page-type map cache, typed fields. These are the spec's real bet, and the part not already covered by existing tools.
  • openlibrary.org needs replacing.
